# Data model

The schema in `backend/migrations/`, the row structs in
`backend/internal/store/`, and the invariants each table holds. Where a column
carries one of Simplifi's own field names (as the import reads them from its
client-side store), this document names it; [§9](#9-how-simplifis-shapes-map-onto-ours)
lists every place the shape differs from Simplifi's, with the reason. Read
[`calculations.md`](calculations.md) for what each stored figure is *for*.

---

## 1. Conventions

The schema is SQLite, in `backend/migrations/sqlite/`: the initial migration
is the whole schema, and every later migration is hand-written. Together they
hold one trigger (`transactions_category_from_pair`, which clears a
pairing-filed category when a person changes it) and no enum types. Every
table is `STRICT`, and the header of the initial migration lists the storage
class of each kind of value. These are the conventions the migrations and the
store hold to.

| Convention | Rule |
| --- | --- |
| Money | `INTEGER` hundredths, so SQL compares, orders and sums it exactly. Never float. In Go it is `domain.Money`, a distinct type over `shopspring/decimal` with no `FromFloat`, converted to and from the column only by `internal/dbconv`. The API serializes it as a JSON string. |
| Rates and quantities | `TEXT` holding the exact decimal: FX rates, share counts, security prices, interest rates. Not money, and they need the places. `domain.Rate` in Go. |
| Dates and timestamps | `TEXT`: a date as `YYYY-MM-DD`, a timestamp in UTC with microseconds at a fixed width, so comparing the text orders them. Each carries a `CHECK` on its length. |
| Primary keys | a uuid, as `TEXT`, generated by the application rather than by the database, so an import can set foreign keys before it writes. Pure edge tables use a composite key of their two ends. |
| Enums | Stored as **text**, with the Go constant as the source of truth. A handful of closed sets also carry a `CHECK` (`cash_flow_forecasts.method`, the connectors' `second_factor` and `sign_in_paused_for`). |
| Booleans | `INTEGER` 0 or 1, `NOT NULL` with a default. The deliberate exceptions are three-state: a rule's `set_*` actions and a filter item's `state`, where null means "not stated". |
| Id lists | A JSON array of ids in a `TEXT` column, deliberately **not** foreign keys. See [§5](#5-spending-plan). |
| JSON | `TEXT` holding a JSON document, for the few values with no fixed shape. |
| Timestamps | `created_at` and (on mutable rows) `updated_at`, defaulted by the database's `now()`; the store sets `updated_at = now()` in each update. |
| Soft delete | `is_deleted` on the user-facing entities (spaces, connections, institutions, accounts, transactions, categories, tags, filters, rules, series, goals, watchlists, securities, guidance). Reads filter it; a soft-deleted row still resolves when something older points at it. |
| Secrets | Sealed before they reach the database (`internal/store/encryption.go`): the SimpleFIN Access URL, connector sessions and passwords, a mailbox's secret, the assistant's API key, TOTP seeds and secret server settings. Each sealed value is bound to its row, so a payload copied into another row does not open. |
| Tenancy | `space_id TEXT NOT NULL`, a foreign key to `spaces` with `ON DELETE CASCADE`, indexed (usually as the lead column of a composite index). There is no autostamp hook: every query names its space, and `store.SpaceID` is a distinct type so a query that forgets does not compile. |

Every table carries `space_id` except these:

- `spaces`: the tenancy root. It holds the household's `primary_currency`,
  `timezone`, `default_date_range` and `sidebar_account_types`, and the setup
  guide's `setup_guide_dismissed_at` and `setup_guide_skipped`. Deleting a
  space (`store.DeleteSpace`) is one `DELETE` the cascade carries to every
  row, after the rows of the tables with a restricting key.
- `users`: a login spans spaces; `memberships` (role `owner`, `admin`,
  `member` or `viewer`, plus that person's `dashboard_layout`) is what grants
  access, unique on `(space_id, user_id)`. `locale`, `theme`, `privacy_mode`,
  `swipe_left_action`, `swipe_right_action`, `animation_duration_ms` and
  `toast_duration_ms` are presentation preferences kept on the account so they
  follow a person between devices; `PATCH /auth/me` writes them,
  `animation_duration_ms = 0` means no animation anywhere, and
  `toast_duration_ms` (1 to 60 seconds) is how long a toast stays before it
  dismisses itself. Every column is written by a narrow store method
  (`UpdateUserProfile`, `TouchLastLogin`, `SetUserPassword`,
  `LinkOIDCIdentity`, `SetUserActive`), never by a whole-row update: a login
  reads the row before a bcrypt verify, and writing every column back from
  that read would restore a password hash changed in between and clear the
  `sessions_valid_from` cutoff the change set. Email is unique
  case-insensitively; `(oidc_issuer, oidc_subject)` is unique.
- `passkeys`, `recovery_codes`: a login's own credentials, keyed by `user_id`
  for the same reason `users` is.
- `revoked_tokens`, `server_settings`, `backup_runs`: the deployment's, not a
  household's. Signed-out token ids that must survive a restart (keyed by
  `jti`, swept by `expires_at`), the settings every space shares (keyed by
  `key`, value sealed: the single sign-on provider, and the backups'
  `backup_at`, `backup_keep_days` and `backup_recipients`, the last a JSON
  list of age public keys with a label and the time each was added), and the
  history of the server's nightly and requested backup runs (status, set
  name, size, error; the newest 200 are kept). The backup sets themselves are
  files, each with its own manifest, not rows.
- `merchant_catalog`: what a merchant's item number means, keyed by
  `(merchant, sku)`. An item number means the same thing in every household.
- `transaction_tags`, `split_tags`, `goal_funding_accounts`: pure edges. Both
  ends are already scoped and an edge cannot outlive either.

## 3. Filter

Ground rule 3. One reusable entity, referenced by id from every surface that
asks "which transactions?". It is the reason an envelope spans six categories
and a watchlist is "by category, payee or tag" with no special-casing
anywhere.

**The owner holds the reference.** `filter_id` lives on the thing that uses
the filter, never the other way round:

| Owner | Column | `filters.scope` | On delete of the filter |
| --- | --- | --- | --- |
| envelope | `envelopes.filter_id` (not null) | `envelope` | `RESTRICT` |
| watchlist | `watchlists.filter_id` (not null) | `watchlist`, or a saved report's `report` filter | `RESTRICT` |
| rule | `rules.filter_id` (not null) | `rule` | `RESTRICT` |
| guidance note | `assistant_guidance.filter_id` | `guidance` | `RESTRICT` |
| automation | `assistant_automations.filter_id` (null is every row) | `automation` | `RESTRICT` |
| saved report | none; the filter is the report | `report` | — |

`saved_view` and `ad_hoc` (a register search) are the other scopes. The
`/filters` API accepts only `envelope`, `watchlist`, `report`, `saved_view`,
`rule` and `ad_hoc` from a client, so a filter cannot claim to be a report it
was not saved as; `guidance` and `automation` filters are written by their own
routes. An `envelope` or `watchlist` filter must keep at least one item,
because a filter with no items matches everything and money derives from
those two.

`filters` also carries a `name`, a soft delete and the raw `query_text` when
the filter came from the search box, so the box repopulates with what the user
typed rather than a re-rendering of the parse.

A `saved_view` filter is one of the register's custom quick filters, and a
Simplifi saved view imports as one. `filters.position` is the order the person
arranged them in, with creation order breaking ties; `GET /filters?scope=`
lists one scope's live filters in that order.

`filter_items` is one condition each, ordered by `(group_index, position)`.
**Items in one `group_index` are AND'd; the groups are OR'd with each other.**
The rules builder's **+** adds an alternative condition set, which has to
*widen* what a rule catches. Everything defaults to group 0, so a filter
nobody grouped is a plain conjunction.

Values land in typed columns rather than a JSON blob, so an envelope that stops
matching is debuggable with a `JOIN`. The evaluator is
`internal/domain/filters.go`; its `FilterItem` is what the columns
reconstruct (`store.DomainFilter`):

| Column | `domain.FilterItem` | Holds |
| --- | --- | --- |
| `field` | `Field` | one `domain.FilterField` |
| `operator` | `Operator` | one `domain.FilterOperator`: `in`, `contains`, `is_exactly`, `equals`, `between`, `greater_than`, `less_than`, `is_true`, `matches` |
| `value_ids` | `Values` | category, tag or account ids, as a JSON array (`json_each` joins it) |
| `value_texts` | `Values` | payee names, statement names, flag colours |
| `text` | `Text` | the substring a `text` item looks for |
| `amount_min` / `amount_max` | `Minimum` / `Maximum` | the amount band |
| `date_from` / `date_to` | `Start` / `End` | an absolute range |
| `date_preset` | — | a **relative** token (`this-month`, `-30d`), resolved to a range before evaluation, so a saved report that means "this month" keeps meaning this month |
| `state` | `State` | the Advanced facet's yes/no pairs |
| `negated` | `Negated` | inverts this item alone, not its group |
| `group_index` | `GroupIndex` | the OR group |

The fields are `category`, `payee`, `statement_name`, `tag`, `has_tag`,
`account`, `flag`, `text`, `amount`, `date`, and the state fields
`is_bill_or_subscription`, `is_excluded_from_reports`,
`is_excluded_from_spending_plan`, `is_reviewed`, `is_pending`,
`is_uncategorized`, `is_category_undetermined`, `has_category_suggestion`,
`has_attachment` and `is_missing_receipt`. The store reads and writes them through the same
constants the evaluator uses, so the two cannot drift.

`is_uncategorized` and `is_category_undetermined` never match a paired
transfer leg: pairing files the leg under Transfer or Credit Card Payment
(see Transfers below), and a leg left without a category, a split one or one
a person cleared, counts toward nothing either way, so it is not waiting for
one. Both read `Transaction.PartNeedsCategory`, as do the uncategorized
alert's count and the assistant's `uncategorized` search; the register's
`isUndetermined` asks the same of `transfer_pair_id`, and shows an
uncategorized leg's category as *Transfer*.

`has_attachment` is true for a row with any `transaction` or `receipt`
document link, the same definition the register's paperclip count reads, so a
hand-attached file and a bill statement or order invoice filed as a receipt
both count. Like `has_category_suggestion` it is not on the row: it is loaded
for the space only when a filter tests it, and a split row takes its parent's
value. `is_missing_receipt` is a row `domain.ReceiptStatusOf` answers
`missing` for (see *Receipts* in [§7](#7-accounts-and-connectivity)), loaded
the same way. Rules, guidance notes and automation triggers refuse all three
fields, along with
`is_bill_or_subscription`, because they judge a row as it arrives and carry
none of these facts.

`statement_name` and `payee` are separate fields on purpose: the rules builder
makes the user choose between "Original statement name" and "Quicken name",
and a rule that matched on the display name would stop firing the moment its
own rename landed.

## 4. Ledger

### Transactions

The four pairs the register cannot get wrong:

| Pair | Meaning |
| --- | --- |
| `statement_name` / `payee` | the bank's immutable string / the editable display name. Matching reads the first, display reads the second. |
| `date` / `effective_date` | when it posted / when it counts for cash flow. The register shows the first, reports read the second. `effective_date IS NULL` means "same as `date`", resolved once, in `domain.Transaction.ReportingDate`. |
| `excluded_from_reports` / `excluded_from_spending_plan` | independent of each other, and of the account's, the category's and the rule's pairs. |
| `series_id` / `series_due_on` | the series **and** the date slot (Simplifi's `stModelId` and `stDueOn`). Matching on the series alone would mark both of a twice-monthly bill's occurrences paid by whichever posted first. |

Also carried: `source` (`domain.Source`: `sync`, `manual`, `file_import`,
`simplifi_import`, `email`, `opening_balance`, `balance_adjustment`),
`external_id`, `is_reviewed`, `is_pending`, `is_deleted`, `is_bill`,
`is_subscription`, `user_flag` + `user_flag_note`, `receipt_not_needed` (see
*Receipts* in §7), `check_number`, `notes`,
`amount_primary` + `fx_rate_used` (the amount in the space's primary
currency), a stored running `balance`, and `rule_id`, the rule that last
wrote the row.

**Estimates.** `estimate_status` marks a row that is not money that moved:
`projected` is a forecast of an unpaid series occurrence, dated on its due
date; `skipped` is the tombstone of an occurrence the user skipped.
`accepted_on` and `expires_on` go with them. A row with any
`estimate_status` is excluded from balances and totals: `store.MoneyMoved`
(`NOT is_deleted AND estimate_status IS NULL`) is the SQL half of
`domain.CountsTowardBalance`, and every hand-written query uses it, because
`NOT is_deleted` alone admits forecasts.

**What the provider said is kept whole.** A field the feed sent is not ours to
discard: a re-sync reaches only as far back as the connector's window, so a
field dropped on arrival is gone.

| Column | Meaning |
| --- | --- |
| `memo` | the provider's second line about the charge, verbatim. The bank's words, like `statement_name`; `notes` is the household's, and two authors need two fields so an edit to one never destroys the other. Often the only thing that says what a thin card line was for. |
| `transacted_on` | when the purchase happened, where the feed states it separately from when it posted: a third date beside `date` and `effective_date`, and the provider's fact rather than ours. Null when the feed drew no distinction. |
| `provider_extra` | JSON: everything else the payload carried, such as SimpleFIN's `extra` object and any key a connector adds. Never a copy of what already has a column, so "unmapped" stays meaningful. |

The assistant reads all three when it categorizes (`nameLookup.transaction`
in `internal/api/automation_host.go` passes `provider_extra` as `bank_data`),
each omitted when empty, so a bank-supplied category or MCC reaches it without
a schema change.

**The category check.** `category_checked_at` and `category_check_note` record
that the assistant's category check last finished on the row without filing
or proposing anything, and why; `category_check_run_id` is the automation run
that last decided the row's category, for the register's "why". The
automations service owns all three and `UpdateTransaction` does not write
them. "Undetermined" is that pair on a row still uncategorized: derived, never
stored, so filing the row by hand clears it. Only a run that reached no answer
writes the pair; a run that settled the row without proposing anything (a
paired transfer leg, a category the history or the model's answer confirms)
clears it. A payee
whose history is transfers, or money in on a credit card under a payment's
wording, is an answer: the check proposes Transfer or Credit Card Payment.

**The settle mark.** `needs_settle` says a row has arrived but has not been
through `settleNewRows`: the cash-flow date, the rules, the series
match, transfer pairing and the running balance. It is written in the same
statement as the row and cleared by the settle, last, once every step has
succeeded, so a failed settle leaves the backlog on disk rather than in the
memory of the run that failed. The next sync settles the backlog before it
reads the bank; `service.SettleBacklog` does the same without a connection,
for an account whose credential has expired. A partial index on
`(space_id, created_at) WHERE needs_settle` makes "is anything owed?" free,
since the answer is normally no rows.

**Transfers.** `transfer_pair_id` is a **token, not a foreign key**, written
on both legs, and either leg may be deleted first. A leg whose partner is
deleted must be released, or it is excluded from income and expense forever
while being ineligible to re-match; `domain.FindOrphanTransferLegs` finds such
legs and `POST /transfers/orphans/repair` releases them. `manual_transfer_pairs`
records the pairs a person joined by hand (`store.PairTransactions` with
`byHand`), keyed by
the pair token, so the automatic pairing never undoes them.

Pairing files each uncategorized, unsplit leg under the space's Credit Card
Payment category when either leg is on a credit card, and under Transfer
otherwise (`domain.TransferCategoryFor`), and sets `category_from_pair`.
Releasing a pair, by unlinking it, by repairing an orphan or by deleting the
other leg, clears the category only where that flag is set, so a category a
person chose survives. The flag needs no care from the write paths: a
`BEFORE UPDATE OF category_id` trigger clears it whenever a statement changes
the category without setting the flag itself, so a person who refiles a leg,
even under Transfer, owns that category from then on.

**Refunds.** `transaction_refund_links` joins a credit to the charge it gives
back (`refund_txn_id`, `charge_txn_id`, never the same row). One row holds
both ids, so unlike a transfer it cannot half-exist; deleting either
transaction drops its links in the same database transaction.

**Padding.** `padded_txn_id`, on the income row a padding mail rule writes,
names the purchase it pads (a foreign key to `transactions`, `ON DELETE
CASCADE`, never the row itself, at most one pad per purchase by a partial
unique index). Only `store.LinkPadding` writes it, re-checking both rows
against the space. `store.DeleteTransaction` soft-deletes a purchase's pad in
the same database transaction, because the pad only says the paycheck was net
of that purchase; `store.RetireDuplicate` releases it, since the surviving
row is still the money that left. A deleted row carries no link. The link is
not `transfer_pair_id`: a transfer is neither income nor expense, and the pad
is income.

Indexes, chosen from the access paths that exist:

```
UNIQUE (account_id, external_id)              the sync's dedupe key
       (space_id, account_id, date)           the register
       (space_id, effective_date)             reports
       (space_id, transfer_pair_id)           pair repair
       (space_id, category_id)                category rollups
       (space_id, series_id, series_due_on)   occurrence matching
       (account_id, date, amount)             the Simplifi relink overlap
       (space_id, created_at) WHERE needs_settle
UNIQUE (padded_txn_id) WHERE padded_txn_id IS NOT NULL
```

The relink index exists because imported rows carry no SimpleFIN
`external_id` for the unique key to catch, so relinking an account also
dedupes on date and amount.

`transactions.account_id` is `ON DELETE RESTRICT`: an account with rows is
soft-deleted, never removed, because a deleted account's rows still resolve
into reports.

### Splits

`transaction_splits` rows (`position`, `amount`, `category_id`, `memo`) carry
their own category and, through `split_tags`, their own tags. The parent's
`category_id` is null when splits exist; reports read the splits when present
and the parent otherwise, so a row is never counted twice. A split path asks
the category predicates per split.

### Categories

`kind` is `income`, `expense` or `transfer` (`domain.CategoryKind`).
`parent_id` nests them (three levels in practice). `txf_id` + `txf_ids` are
Tax eXchange Format codes, adopted verbatim: the Taxes report is a grouping
over that field. `known_category_id` is Simplifi's stable system marker, and
is what keeps "this is the Transfer category" working after the user renames
it; losing it on import would turn every card payment back into an expense.
`is_user_assignable` is false for the system categories the engine writes
(Opening Balance, Balance Adjustment); `is_editable` guards the rows the user
may not rename.

**Protected categories.** A category a process depends on cannot be deleted,
by `DELETE /categories/{id}`, by the unused-category purge or by the store
beneath both (`store.ErrCategoryProtected`). `domain.CategoryProtection` is
the whole rule, and the API returns its answer as `protected_reason`:

| Category | Marker | Why |
|---|---|---|
| Transfer | `7125000000` | matched transfers are filed under it |
| Credit Card Payment | `7125250000` | matched credit-card payments are filed under it |
| Fees & Charges | `3000000000` | the fee alert watches it |
| any row with `is_editable` false | | maintained by the app |

The three marked categories may be renamed and re-parented, since the
processes find them by marker, but their `kind` is fixed: Transfer turned
into an expense would make every matched transfer spending. There is no column for
the protection; it is derived, so it cannot disagree with the marker.

Every space a person opens (the account's own space at sign-up, one an
administrator creates with an account, and one made from the space switcher)
starts with the default tree, `domain.DefaultCategories`: two levels of
income and expense categories carrying the `known_category_id` and `txf_id`
Simplifi's export gives the category of the same name, with Federal Estimated
Tax Payment not editable, as in Simplifi. Simplifi's export has no transfer
category, because its transfers name the other account; the tree adds
Transfer with Credit Card Payment beneath it, both of kind `transfer` and
excluded from reports and the spending plan, under markers of this app's own
in Simplifi's scheme. `store.CreateSeededSpace` writes it through
`SeedCategories`, which skips every path the space already has and every
marker of a protected category the space already carries (so a renamed
Transfer is not seeded twice), so seeding is idempotent; **Start with the
standard set** on an empty category list runs the same seed. Joining a space
that exists seeds nothing, and `agentifi import` creates its space with the
export's categories, adopting a root category named Transfer as the app's
own and adding whichever of the two transfer categories it still lacks.

`excluded_from_reports` and `excluded_from_spending_plan` are the category's
own pair, the third level of ground rule 4 (Simplifi's
`isExcludedFromReports` and `isExcludedFromBudgets`).
`domain.Category.CountsAsIncomeOrExpense` and `CountsTowardSpendingPlan` read
them, and are what the report, watchlist and plan predicates ask; the flags
reach the domain through `store.DomainCategory`, and a field dropped there is
a switch that silently does nothing.

`excluded_from_category_list` is a display flag, not one of the pair: it hides
the category (and its subcategories) from the picker that files a transaction
without changing a number. Filters still offer it, so rows filed under it stay
findable.

### Tags

`tags` are per space, unique on `(space_id, name)`, with an optional `color`.
They attach to rows through `transaction_tags` and to splits through
`split_tags`.

### Rules

Conditions live in a `Filter` (`rules.filter_id`), not in columns of their
own. Rules run in `priority` order when active. Every action column is
nullable and null means "leave alone": `set_payee`, `set_category_id`,
`set_notes`, `set_is_reviewed`, and the two exclusion actions, which need all
three states (set it, clear it with *Include everywhere*, or leave it).
`add_tag_ids` is a JSON array of tag ids added to the row's tags. `source_ref` names the
Simplifi record an imported rule came from and is unique per space when
non-empty, which is how a second import recognizes a rule it already wrote.

## 5. Spending plan

**Materialized, one row per month.** `spending_plan_months` is unique on
`(space_id, month)` and has 55 columns, which is the point: a closed-out month
must be able to disagree with what a recalculation would say today.

Seven buckets (`income`, `bills`, `subscriptions`, `transfer`, `goals`,
`planned_spending`, `spent`), each with the same five fields:

```
calculated_<bucket>_amount     what the engine computed
<bucket>_txn_ids               the exact rows that contributed: the audit trail
excluded_<bucket>_txn_ids      rows dropped for this month only, unmutated
overwritten_<bucket>_amount    a user override that wins over the calculation
reset_overwritten_<bucket>     clears the override without losing it
```

Dropping any one of the thirty-five collapses the design back into a view.

Plus: `calculated_rollover_amount` (carried in from the prior month's
`left_to_spend_amount`), `set_aside`, `total_to_spend_amount`,
`left_to_spend_amount`; the projection block (`projected_other_spending`,
`projection_type` of `run_rate`, `prior_month` or `average_n_months`,
`projection_start_date`, `projection_end_date`, `projection_buffer`,
`projection_window_months`); and `is_closed_out` with `closed_out_at`,
`show_closed_out`, `new_month_viewed`, `hide_excluded_from_ui`.

The `*_txn_ids` columns are JSON arrays of ids, not join tables and not foreign keys. A
closed month has to keep saying which transactions it counted after one is
deleted, and a foreign key would cascade that evidence away. The price is a
possible dangling id; the alternative is a month whose stored total no longer
reconciles with its own evidence.

### Envelopes

Simplifi's `plannedSpendingItems`, in a table of their own keyed to the month
by `spending_plan_month_id` (`ON DELETE CASCADE`). Per month, because closing
a month has to freeze what its envelopes said, and one mutable envelope row
cannot.

Each carries a `name`, `filter_id` (which transactions it covers),
`target_amount`, `overwritten_target_amount`, `calculated_spent_amount`,
`txn_ids` / `excluded_txn_ids`, `hide_excluded_from_ui`, `recurring`, and
`rollover_amount`: **a stored, editable amount, not a boolean**. *Release
unspent funds*, *change rollover amount* and *auto-release*
(`auto_release_rollover`) are three operations, none expressible as a flag on
the target. `rollover_is_carried` says the figure is the engine's carry from
the prior month, so it follows that month while both are open; once the user
sets or releases it, it is theirs and is never recomputed.

`recurring_group_id` is what a recurring envelope keeps across months, so the
UI can show its history. Null for a this-month-only item.

## 6. Series

A series is a recurring bill, subscription, income, transfer or card payment
(`kind`: `domain.SeriesKind`) on one `account_id`. RRULE fields are columns,
not a serialized rule string:

```
alias           the dropdown label (EVERY_MONTH, TWICE_A_MONTH, ...), round-tripped
frequency       DAILY / WEEKLY / MONTHLY / YEARLY, or NULL for one-time
interval        the every-N
by_month_day    integer[]  how "twice a month" and "multiple fixed dates" work
by_day          varchar[]  RRULE BYDAY codes, not weekday integers
by_month        integer[]  active months (1-12), RRULE BYMONTH; empty is every month
start_on, end_on, next_due_on
```

Two names, for the same reason a transaction has two: `description` is the
matching input and is never rendered; `display_name` is the label and is never
matched against (display reads `display_name` or else `description`).
`learned_descriptions` holds the statement wordings already linked, because
"Paycheck" shares nothing with "ACME CORP DES:PAYROLL".

Match tolerance is separate from the wording match: `match_criteria`
(`exact`, `any`, `range`, `auto`) with `match_amount_min` /
`match_amount_max`.

`override_next_due_on` / `override_next_amount` let one occurrence differ
without forking the series. A series joined to a billed account through
`series_bill_links` (one series per billed account, one billed account per
series) takes each open or paid bill's amount due on the slot whose match
window holds the bill's due date (`domain.SlotBill`); `auto_adjust_due_on`
also shows the slot on an open bill's due date. An override still wins over
both, on the slot it applies to. `reminder_days` and `auto_accept_days` drive the
reminder and the auto-accept of a projected occurrence.

The embedded transaction template is flattened into typed columns
(`template_payee`, `template_notes`, `template_tag_ids`, the two
`template_excluded_from_*` flags) over the series' own `account_id`,
`category_id`, `amount` and `currency`. Only `template_splits` is JSON, being
the one part with no fixed arity.

`suggestion_dismissals` belongs beside series: the Suggested tab re-derives
its proposed series on every read, so a dismissal is keyed on the group's
`signature` (account, direction, currency, kind, matched wording) rather than
on a row, and a new charge joining the group does not resurrect it.

## 7. Accounts and connectivity

### SimpleFIN connections

`connections` is **SimpleFIN only**: one Access URL, sealed at rest
(`access_url_encrypted`). No provider column, no OAuth state, no widget
callback. One Access URL spans every bank linked at the Bridge, so
`sync_errors` (JSON) records failures per institution while the connection
stays usable, and `retry_not_before` is the self-throttle. `status`
(`store.ConnectionStatus`) is `active`, one of the two failures SimpleFIN
raises (`credentials_expired`, `rate_limited`), or `pending_link`: a claimed
connection whose accounts nobody has yet matched to the household's own, and
nothing imports until somebody says which is which.

`ignored_remote_accounts` refuses an account the Bridge reports before an
account row is ever made, keyed by `(connection_id, external_id)`.

`institutions` are made by the sync (`EnsureInstitution`) and by the Simplifi
import as reference data; `hide_below_balance` is the one column a client
writes there.

### Accounts

`accounts` splits what an account *is* from what it is *called*:

- `kind` drives arithmetic (`domain.AccountKind`: `cash`, `credit_card`,
  `loan`, `investment`, `asset`).
- `type` is the picker label (`roth_ira`, `home_equity_loan`) and never
  appears in a calculation. Adding a type is data, not a code change.
  A health savings account has two: `hsa` (Banking, kind `cash`) is the
  checking-style account the debit card draws on, and `hsa_investment`
  (Investments) is the brokerage its cash may be swept into. A CSV import or
  a SimpleFIN account named as an HSA is the banking side unless the name says
  brokerage or investment, or the account holds securities. The one place a
  type is read is the receipts default below.

`logo_url` is replaced on every sync; `custom_logo_url` is the household's
own and wins wherever a logo is drawn. `usage_type` and `exclude_bank_pending`
are carried from the Simplifi import and editable, and nothing branches on
either. `requires_receipts` holds the account's spending rows to a receipt; see
*Receipts* below.

**Balances.** `provider_balance` (with `provider_balance_at`) is stored
**already sign-normalized**, debt negative (Simplifi's `normalizedBalance`);
null means manual, and for a manual account the transactions *are* the
balance. `opening_balance` + `opening_balance_on` are used verbatim when the
user states them. `goal_balance` holds the savings-goal reserve;
`pending_holds` the authorizations that cut available funds without posting.

`withheld_balance` + `withheld_balance_at` hold a provider figure the sync
refused to apply: a connected account with a stable, material balance that
suddenly reports 0.00 is almost always the aggregator dropping a figure, so
the sync keeps the last-known balance and records the zero here, with when it
was first seen, unless the account's own transactions explain it
([`calculations.md` §3](calculations.md)). `withheld_balance_reason` is the
sentence saying what the zero was compared with; empty when nothing is held.
`accept_zero_balance` is the household saying the zero is real for this
account, which lets it through.

**History start.** `history_starts_on` is the household's override of where
the account's balance history begins; null is automatic, and automatic is
derived, never stored ([`calculations.md` §4](calculations.md)). It is not
`opening_balance_on`, which dates a figure rather than the history, and not
`sync_floor_on`, which only stops a sync creating rows before it.
`history_rebuilt_from` is the start the account's `balance_snapshots` were
last trimmed and filled for; the daily pass rebuilds any account where the two
differ, and a null means the account has not been rebuilt yet.

**Secured loans.** `secured_by_account_id` is on the loan, naming the asset it
is secured on (`ON DELETE SET NULL`: selling the house must not delete the
mortgage). The account API answers the pairing as an `equity` block on the
asset. `property_address`, `vehicle_vin` and the `vehicle_mileage*` columns
are what an outside valuation source needs to price a physical asset;
`valuation_source` + `valued_at` name the provider behind the current balance,
and a manual revaluation clears them.

**Card fields.** `credit_limit`, `statement_balance`, `minimum_due`,
`due_date`, `interest_rate` (a rate, exact decimal text) and
`statement_close_day`, the fallback for a charge's `effective_date` when there
is no due date. SimpleFIN's spec has no statement, so each comes from a
narrower source:

| Column | Source |
| --- | --- |
| `credit_limit` | the Simplifi import (`creditLimit`), a connector's `extra`, or the account dialog. It is the only input to `credit_used_pct`, so without it there is no credit gauge. |
| `interest_rate` | the Simplifi import (`interestRate`), a connector's `extra`, or the dialog. `domain.APRAsRate` reads 24.99 and 0.2499 as the same figure, because neither source says which scale it used. |
| `statement_balance`, `minimum_due` | a connector's `extra`, a bill on a linked billed account (below), or the dialog. Amounts owed, stored as magnitudes, so they read as positive beside a card balance that is already negative. |
| `due_date` | a connector's `extra`, a bill on a linked billed account, or the dialog. Never derived from `statement_close_day`: the grace period is a term nothing stores, so a computed due date would be a guess printed as a fact. |
| `statement_bill_id` | the bill the three statement figures were copied from, or null for figures typed in, reported by a connector, or absent. Written with them by `service.Bills.Ingest`; cleared by a hand edit of any of the three and by a sync that reports one. The account API answers it as `statement_source`. |

`bill_subaccounts.account_id` links a billed account to the household account
it is: a `credit_card` or `loan`, at most one billed account per account (a
partial unique index), set null when the account is deleted. It is not
`bill_connections.autopay_account_id`, the account that pays. A bill ingested
on a linked billed account (mailed, pulled or typed) writes
`statement_balance` (the bill's `amount_due`), `minimum_due`
(`bills.minimum_due`) and `due_date` through `domain.StatementAfterBill`: a
later due date replaces all three, the same due date refreshes only what a
bill wrote, and an earlier one never writes.

`accounts.provider_extra` keeps the account's unmapped payload for the same
reason `transactions.provider_extra` does. The sync writes a statement figure
only when the payload carried one, so a hand-entered figure survives every
sync that learns nothing.

**Flags.** Four independent ones: `excluded_from_reports`,
`excluded_from_spending_plan`, `excluded_from_account_bar`,
`include_in_net_worth`. Every combination occurs. Beside them:

- `hide_below_balance`, on both `institutions` and `accounts`: the threshold
  under which an account is left out of the account lists
  ([`calculations.md` §3](calculations.md)). It sits on the institution
  rather than the connection because one SimpleFIN connection spans every
  linked bank. The account's value overrides its institution's, `0` there
  means "always show", and null at both levels is no rule. The API answers
  the outcome as `hidden_small_balance`. Display only: no total, report or
  filter reads it; the account lists and the pickers that file something
  into an account leave the row out behind a reveal.
- `default_register_tab`: the register tab the account opens on — `all`,
  `spending` or `income` — null opening on the rows. A link that names a tab
  outranks it.
- `ignored_at`: when the household ignored the account; null is not ignored
  ([`calculations.md` §3](calculations.md)). It takes an existing account out
  of every list and figure without deleting it or its history, and is
  distinct from `is_closed` (a closed account still counts in net worth), from
  `is_deleted`, and from the four flags, whose values it leaves alone. Only
  `store.SetAccountsIgnored` writes it; the whole-row `UpdateAccount` a sync
  makes cannot.

**Relink and sync position.** `simplefin_account_id` and `sync_floor_on` are
set together, by the match step, never by the import. The first sync after a
link reads a month behind the account's newest row, and without the floor
that month would land on top of history the import already wrote. The floor
refuses only the *creation* of a row dated before it; reading those days and
settling a row already held stay allowed.

`synced_through_on` is the last day a sync read the account through without
failing, cleared by a link and an unlink. Each sync resumes from the later of
it and the newest row, less a 30-day overlap, so a routine run asks the Bridge
about one month in one request. Anything wider (a first link, a catch-up) is
walked by `provider.SimpleFin.Transactions` in windows of at most 45 days,
oldest first, with a row repeated across two windows kept once, because the
Bridge warns on wider requests.

### Balance history and FX

`balance_snapshots` is one account's balance on one day, materialized
nightly, unique on `(account_id, as_of)`. The row dated `D` is the balance at
the end of `D` by posted date; the trailing week is re-derived on every pass,
so a row converges on its day's close within a week (see
[`calculations.md` §12](calculations.md) before reconciling it against
Simplifi's daily balances). `anchor_on` + `anchor_balance` record the provider
figure a derived row was walked back from. `is_imported` marks a row the
Simplifi import carried over: an observation a rebuild never deletes, and the
earliest of which is evidence of the history start. No derived row predates
the account's history start.

`fx_rates` holds one rate per `(space_id, base_currency, quote_currency,
date)`, with its `source`; `transactions.amount_primary` and `fx_rate_used`
record the conversion a row was given.

### Bill providers and the mailbox

One `bill_connections` row per login at a provider (`biller`, a `label`, sealed `session_state` and `credential_sealed`, the pull
schedule and its last outcome, the second-factor and sign-in-paused state);
`bill_subaccounts` are the billed accounts that login reaches; `bills` are their statements, one per
`(subaccount_id, due_on, invoice)` (`invoice` is empty unless the provider
bills separately on one day), with `amount_due`, `minimum_due`, the period,
its `source`, and `marked_paid_at`, a person's word that it was paid where
the ledger cannot see, which only `POST /bills/statements/{id}/paid` writes
and which ends its pay-manually reminder
([calculations §9](calculations.md#pay-manually-reminders)).
`bill_payments` are the payments a medical provider lists for a
billed account, unique on `(subaccount_id, external_id)`, each with the bank
row it was paired with (`transaction_id`, unique, `ON DELETE SET NULL`).
`bill_challenges` is a sign-in waiting on a code from a person.
`email_connections` are the watched mailboxes, `mail_rules` read a bill or a
payment out of a message, and `bill_emails` is the log of each message seen
and its `outcome`, unique on `(connection_id, message_id)`. See
[`connectors/bills.md`](connectors/bills.md).

`documents` is one stored file's metadata (the bytes live in the storage
provider under `storage_key`), deduplicated per space by `content_sha256`.
`document_links` attach it to a `bill`, `transaction` or `merchant_order`,
or file it on a bank row as a `receipt` (`kind` is a closed set validated in
the store, since the polymorphic target has no foreign key). A `transaction`
link is a file a person attached. A `receipt` link, whose target is a
transaction, is derived: `role` `statement` for the statement of the bill
whose slot the row settled or that the bill payment paired with the row
paid, `invoice` for the invoice of a merchant order the row was matched to
(never a refund's match). Only
`store.ReconcileReceipts` writes or removes one; the bill, series-link,
match, document-link and transaction writes call it for the rows they touch,
and the scheduler runs it over each space on its first pass and daily. One
file can therefore belong to a bill and to the bank row that paid it.

An upload is sniffed from its bytes and kept only if it is JPEG, PNG, GIF,
WebP, HEIC, HEIF or PDF, at most 25 MB (`service.AllowedDocumentTypes`,
`service.MaxDocumentBytes`). HEIC and HEIF, which the browser's own sniffing
does not know, are recognised by the major brand of the leading `ftyp` box;
they are stored and served as themselves, and a browser that cannot draw one
shows the file glyph in place of a thumbnail. On a touch screen the
transaction's attachments panel also opens the camera; that is a second
source for the same upload, not a second path.

**Receipts.** `accounts.requires_receipts` says whether every spending row of
the account needs a receipt. Null means the default
(`domain.AccountRequiresReceipts`): true for a cash account of type `hsa`, or
one whose name holds the word HSA or FSA, since an import may type a bank's
HSA as checking; false for every other account, the invested side of an HSA
(`hsa_investment`) included, since its outflows buy funds or carry money back
to the cash side. The account dialog's *Requires receipts* switch writes the
setting, for an invested HSA, an FSA or a card kept for eligible expenses.
`domain.ReceiptStatusOf` decides each row of such an account: a row that
spends (a negative amount) needs one; money arriving (a contribution,
interest, a dividend, a refund), a transfer (a paired leg, a row filed under a
transfer category, a split row all of whose splits are), a forecast, an
opening balance, a revaluation, a deleted row and an ignored account's rows
do not. A row that needs one is `on_file` when any document is behind it, by
`has_attachment`'s definition, so a settled bill's statement or a matched
order's invoice counts; otherwise it is `not_needed` when a person set
`transactions.receipt_not_needed` (a bank fee), and `missing` when not. Every
transaction the API serves carries `receipt_status` (null where no receipt
is asked for). The dashboard's *Missing receipts* tile counts the
`is_missing_receipt` rows over all time and links to the register filtered to
exactly them; the assistant's `search_transactions` reports the status and
takes `missing_receipt`.

### Merchants

`merchant_accounts` is one login at a merchant (`merchant` is `amazon` or
`costco`, never assumed), with its sync schedule, sealed session and
credential, and an optional `gift_card_account_id`; its
`invoice_backfill_at` (null when none has run), `invoice_backfill_filed`,
`invoice_backfill_left` and `invoice_backfill_stopped` (`''` when it reached
the last order) say how the account's last invoice backfill ended.
`merchant_orders` (unique on `(space_id, merchant_account_id,
order_number)`) and their `merchant_order_items`, `merchant_charges` (one
card charge against an order) and `merchant_refunds` arrive from order files
or a connector; an order's `invoice_misses` counts the backfills that
reopened it for its invoice and found none to print, and at three it is not
reopened again.
`merchant_matches` joins a bank transaction to the order (or, with
`refund_id`, the return) it paid for, with the `amount`, the `basis` of the
match and a `confidence`. `merchant_catalog` is the space-free lookup of what
an item number is. See [`connectors/merchants.md`](connectors/merchants.md).

## 8. Goals, watchlists, investments, alerts, forecasts, the assistant

- **`goals`** name one `account_id`, the account whose `goal_balance` they
  inflate, and take further funding accounts through `goal_funding_accounts`,
  because the create flow's *Add Account* repeats the row.
  `is_taken_from_plan` decides whether contributions show in the plan's Goals
  bucket. `txn_ids` is what the goal counts; `withdrawal_txn_ids` and
  `spending_txn_ids` are disjoint subsets of it, and a row in neither is a
  contribution. A withdrawal takes money back out of the reserve, which the
  sign cannot say: money leaving a funding account is a contribution when it
  went to the goal's account and a withdrawal when it paid for what the goal
  was saving for. A spending row records what the money went on, from any
  account, without moving the reserve, and is left out of the spending plan,
  since it was planned outside the month it lands in. `closed_on` is the day
  the user closed the goal, null while it is open: a closed goal reserves
  nothing in its account and adds nothing to the Goals bucket from that month,
  and keeps its rows. `saved_so_far`, `spent` and `contributed_this_month` are
  materialized.
- **`watchlists`** are a `filter_id`, a `name`, an `emoji` and an optional
  `target_amount` over a `period` (with `start_date` / `end_date` for a
  custom one). The aggregates Simplifi stores are derived here
  ([§10](#10-materialized-versus-derived)). The create and edit sheet uses the
  shared filter editor and writes a filter of scope `watchlist` that the card
  owns. A card can instead point at a saved report's filter, and then editing
  the report changes the card; editing that card's facets never edits the
  report, it gets a filter of its own.
- **`securities`** are per space, unique on `(space_id, symbol)`, with
  `last_price` and `prior_close` as rates, not money: a share price is not
  rounded to the cent. **`holdings`** (unique on `(account_id, security_id)`)
  keep `cost_basis` nullable and `is_cost_basis_complete` separate: an
  unknown basis is a state, not a zero, and a partial basis is a number that
  is still untrustworthy. `shares` and `average_cost` are rates. A security
  with holdings cannot be deleted (`RESTRICT`).
- **`security_prices`** is one close per security per day, the history
  `securities` cannot hold. Written by the price refresh and the detail
  screen's backfill, upserted on `(space_id, security_id, on_date)` so two
  refreshes in an afternoon are one close. `ON DELETE CASCADE` from
  `securities`, unlike the ledger's rule for accounts: a quote is a fact about
  the world that can be fetched again.
- **`alert_rules`** is one row of the notification settings screen, scoped to
  a user and optionally an account (a low-balance floor is per account),
  unique on `(space_id, user_id, alert_type, account_id)` with nulls not
  distinct. Channels are three booleans; thresholds are `threshold_amount`,
  `threshold_count` or `threshold_pct`, and which one applies is the
  catalogue's `ThresholdKind` in `internal/domain/alerts.go`, not whichever
  column is non-null. `is_paused` is separate from `is_enabled` so *Pause all*
  does not destroy the choices it suspends.
- **`notifications`** is the feed, deduped on `(user_id, dedupe_key)` because
  alerts are re-evaluated on a schedule. A standing state (a balance below its
  line, an unreadable mailbox) also carries `condition_key`, and a partial
  unique index allows one unresolved row per state per person; setting
  `resolved_at` when the state ends lets its next occurrence be news again.
  Clearing a card (`DELETE /notifications/{id}`, or `DELETE /notifications`
  for the whole feed) stamps `cleared_at` and keeps the row, because the row
  is the dedupe record: a deleted one would be sent again by the next sweep.
  **`push_subscriptions`** are a person's Web Push endpoints, unique on
  `(user_id, endpoint)`.
- **`cash_flow_forecasts`** hold six months of money in and money out as
  `periods` (JSON, one object per month), with a `narrative`. Two kinds of
  row share it, told apart by `method`. `model` is the household-wide forecast
  an assistant automation writes: `account_id` null, append-only, carrying the
  `model` that answered and the automation run behind it. `average` is one
  account's own estimate (`account_id` set, `ON DELETE CASCADE`), recomputed
  from the ledger every night, so saving one replaces that account's previous
  row ([`calculations.md` §8](calculations.md#an-accounts-own-estimate)).
- **The assistant.** `assistant_connections` is the model connection, one per
  space: `base_url`, `model`, a sealed API key, `tool_call_style`,
  `allow_writes` and `apply_without_asking`. A conversation is
  `assistant_conversations` (optionally started by an automation run or from a
  mailbox message) and its `assistant_messages`. **`assistant_actions`** is
  one proposed change, a card: the exact request (`method`, `path`, `body`),
  the model's `summary`, `preview` (the request in words, every id already
  named), `group_id` (the rows one bulk tool call proposed), `resource_id`
  (what the request created or changed), `decline_reason`, and a `status` of
  pending, applying, applied, failed or discarded; the lifecycle is in
  [`assistant.md`](assistant.md#a-cards-life). `assistant_corrections` logs
  what a person chose instead when they changed a category on a card, with the
  wording copied onto the row so it stays readable after the transaction is
  renamed or deleted; it is shown to the model on later runs about the same
  payee, and is not a rule. `assistant_guidance` is a standing instruction
  passed to the model verbatim, scoped by a filter.
- **`assistant_automations`**: `template_key` names the built-in one started
  from. `prompt_from_template` and `description_from_template` mark a text the
  household has not changed from the template's; the store sets them from the
  text on every write, and a marked text is read from the template in code,
  so the stored `prompt` or `description` beside a true flag is not read.
  Each firing is an
  `assistant_automation_runs` row that keeps the prompt it was actually sent,
  its outcome, and for a category decision the `confidence` (the model's own
  figure when it stated one, otherwise the history vote's score) and who
  decided (`decided_by`). A transaction trigger fires at most
  once per automation and row (a partial unique index). `dry_run` marks a run
  whose change tools recorded rather than proposed; `blind` is a dry run shown
  the row with its category hidden, with `expected_category_id` the answer it
  is checked against. `category_result` is what a finished run about a row
  concluded ([`calculations.md` §2](calculations.md)), empty for a dry or
  blind run. `bulk` runs are claimed after every other queued run, so a
  request over a whole ledger does not hold back the rows a sync brings.
- **`category_suggestion_batches`** is one "Suggest categories" request:
  `row_count` is the rows it named, which a run displaced by a later request
  for the same row does not reduce. Its runs carry `batch_id` and
  `reviewed_when_queued`, the row's review state when it was queued, and its
  progress and comparison are counted from them
  (`domain.SummarizeSuggestionBatch`), never stored. A batch over more than
  `domain.BulkSuggestionRows` (200) rows is bulk. `cancelled_at` marks one
  whose unstarted runs were deleted; `dismissed_at` one whose summary the
  household put away. A request that queued nothing keeps no batch.

## 9. How Simplifi's shapes map onto ours

The Simplifi import (`internal/importer`, described in
[`importing.md`](importing.md)) reads Simplifi's client-side stores and writes
them in this schema's shape. Where the shapes differ:

| Simplifi | Agentifi | Why |
| --- | --- | --- |
| `filterStore.parentIds` | not imported; owners hold `filter_id` | The reference direction is already a foreign key from the envelope, watchlist or rule. Two records of one relationship diverge. |
| `plannedSpendingItems` embedded in the month record | `envelopes` table keyed to the month | Same per-month semantics, but joinable and typed. An envelope's filter and rollover are still per month. |
| `freeToSpendStore.goalsIds` / `excludedGoalsIds` | `goals_txn_ids` / `excluded_goals_txn_ids` | The Goals bucket is computed from goal *contributions*, which are transactions (`domain.GoalContribution`). Storing goal ids would lose which contribution counted, so an imported month's goal ids are reported and not stored. |
| `renameRuleStore` | `rules` with a `filter_id`, `source_ref` `simplifi:renameRuleStore:<id>` | The rules builder's conditions are a subset of the filter vocabulary; a second implementation would drift from the register's. `renamePayeeFrom`, `renamePayeeTo` and `matchCriteria` become a statement-name filter and a `set_payee`. |
| transaction rules, and rows' `transactionRuleId` | `rules`, from the rules file when given, otherwise rebuilt from the rows that name them | Simplifi keeps transaction rules on its server, not in the export. The rules file is the saved response to its `transaction-rules` request, passed as `agentifi import --transaction-rules`; a rule found there is the real definition (`source_ref` `simplifi:transaction-rules:<id>`). Without it, each rule is rebuilt from the evidence of the rows it touched (`simplifi:transactionRuleId:<id>`), and a later rules-only import upgrades the rebuilt rule in place. |
| `scheduledTransactionsStore.transaction` (nested template) | flattened `template_*` columns + `template_splits` JSON | A generated occurrence is a real transaction from birth; building one out of a blob would lose the foreign keys. |
| `spendingWatchListStore.thisMonth` / `yearToDate` / `spentSoFar` / `monthlyTrend` / `monthSpendingProjection` | not stored | Cheap to derive, and staleness in them is immediately visible. See [§10](#10-materialized-versus-derived). |
| `accountsStore.isExcludedFromBudgets` | `excluded_from_spending_plan` | Same flag, in this app's vocabulary: "Budgets" is Simplifi's internal name for the spending plan, as `isExcludedFromF2S` is on the transaction. |
| `transactionStore.payee` / `renamedPayee` | `statement_name` / `payee` | Simplifi's names invert the intuition (its `payee` is the bank's raw string). Ours read the way the UI labels them. |
| account statement figures (`statementCloseBalance`, `statementDueAmount`, `statementMinPayment`, ...) | not imported | One cycle's numbers with nothing to refresh them; a statement balance months old is worse than a field that says nothing. Bills and connectors supply them ([§7](#7-accounts-and-connectivity)). |
| `businessId` / `customerId` / `projectId` | not imported | Quicken Business, a non-goal. |
| `fundingAccountStore`, `a2aTransfersStore` | not imported | Real ACH rails; out of scope. |
| `achievementsStore`, `milestonesStore` | not imported | Gamification, no financial value. The `achievement_badge` alert type is in the catalogue so the settings screen matches, and nothing raises it. |
| Credit-score alerts | in `AlertType`, email-only, never raised; imported rules for them are declined | They need a credit-bureau relationship this app does not have. |
| `institutionLoginsStore` | not imported as connections | Simplifi's aggregator links carry no portable credential. Institutions come over as reference data, accounts arrive unlinked, and the live connection is SimpleFIN. |

Alerts Simplifi does not have: `stale_pending`, a pending row that has sat
unsettled too long, which reports a fault in the ledger rather than a fact
about the household's money; and the connector alerts (`amazon_sign_in`,
`costco_sign_in`, `merchant_pull_failed`, `bill_challenge`,
`bill_pull_failed`, `email_connection_failed`) for a pull that has stopped until somebody acts.
There is no alert for a SimpleFIN connection itself; a `credentials_expired`
connection puts a reconnect prompt in front of the user instead.

## 10. Materialized versus derived

Following [`calculations.md` §12](calculations.md):

| Aggregate | Decision | Where |
| --- | --- | --- |
| spending-plan month rows | materialized | `spending_plan_months` |
| transaction running balance | materialized | `transactions.balance` |
| account balance history | materialized | `balance_snapshots` |
| goal `saved_so_far` / `spent` | materialized | `goals` |
| account `goal_balance` | materialized | `accounts.goal_balance` |
| envelope spent within an open month | derived, snapshot on close-out | `envelopes.calculated_spent_amount` |
| watchlist trends and projections | derived | — |
| net worth at a date | derived from `balance_snapshots` | — |
| investment TWR / IRR | derived per request | `GET /performance` |
| an account's own cash-flow estimate | materialized nightly, replacing the last | `cash_flow_forecasts` (`method = 'average'`) |
| a new row's settle backlog | materialized on the row | `transactions.needs_settle` |

Anything materialized owes a recompute function, a list of what triggers it,
and a periodic full rebuild that produces identical output. The
rebuild-equals-incremental test is what keeps materialization honest.

## 11. Migrations

goose, in `backend/migrations/`, embedded in the binary
(`migrations/embed.go`) and applied by `agentifi migrate`, a separate
subcommand rather than a step of `serve` so two instances cannot race to
migrate one database. The schema starts from one file, `00001_initial.sql`,
dumped from a database rather than typed; every later file is an ordinary
forward migration. The initial file creates every table before any
constraint, so its table order carries no meaning. Each migration's
`-- +goose Down` is its exact reverse.

A new migration takes the next number (`00002` is the first after the
initial file), changes the schema in both directions,
and updates `TestSchemaCarriesEveryTable` if it adds or drops a table.
